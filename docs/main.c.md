# `src/main.c`

Status: draft for user approval; version 0.1.3.

## Purpose and dependencies

Starts the GTK4 application, loads the embedded interface, and connects UI events. Depends on GTK4/GLib, `include/subject.h`, the `Edit` hierarchy (`include/edit.h`, for `Edit` and `EditKind`), the subject menu (`include/msc/menuEditKind.h`, which brings in the `Menu` base class from `include/menu.h`), the "Nueva materia" dialog (`include/msc/subjectDialog.h`), and the resource path `/org/studystudio/interface.ui`. The file now opens with a standard header comment (developer, repository, version, license, edit date).

## Current behavior

| Element | Responsibility |
| --- | --- |
| `AppState` | Holds the destination widget (`destiny_content`), the parent window (`window`), the footer label (`footer_label`, used by `app_status`), the `cancellable` passed to every `GtkFileDialog`, and the counter for added subjects. Owned by the window (see [Ownership](#ownership-and-limitations)). |
| `SubjectPanel` | One per subject: its `number` (the `#x` of the label), the owned `Subject` (`NULL` until created), its `GtkMenuButton`, the `GtkRevealer` with the editing area, the `editor_box` where the `Edit` renders, the chosen `EditKind` (see [edit.c](edit.c.md#editor-kinds)) and the open `Edit` (`NULL` if none). Owned by the subject's box through `g_object_set_data_full`; freed by `subject_panel_free`, which also closes the open `Edit` and the `Subject`. |
| `main` | Outside Windows, first ignores `SIGPIPE` (`signal(SIGPIPE, SIG_IGN)`), so a write to a pipe whose reader died (`tar` missing or rejecting the data) fails with `EPIPE` and is reported by `subject.c` instead of killing the application; the `tar` children restore `SIG_DFL` (see [subject.c](subject.c.md#extraction)). Then creates application `org.ejemplo.app`, connects activation, runs the event loop and releases the application. If LibreOffice was started (`edit_doc_started()`, see [editDOC.c](editDOC.c.md)), it flushes `stdio` and leaves with `_Exit(status)` instead of returning, to skip LibreOffice's static destructors, which crash inside `exit()`. |
| `on_window_destroy` | `"destroy"` handler of the main window, run while its children still exist: unregisters the logger (`subject_set_logger(NULL, NULL)`), since `footer_label` is about to die, and cancels `state->cancellable`, so pending file dialogs finish with an error and their callbacks return without touching freed data. |
| `app_state_free` | Destructor tied to the window with `g_object_set_data_full`: runs when the window is finalized, after every panel was freed, and releases the cancellable and the `AppState`. |
| `activate` | Loads the builder resource, retrieves widgets, associates the window with the application, allocates state (with its `cancellable`), ties it to the window and connects `on_window_destroy`, connects signals, presents the window, fetches `footer_label` and registers it with `subject_set_logger(on_subject_log, footer_label)`, and finally releases the builder. |
| `on_subject_log` | Logger callback registered with `subject_set_logger`. Copies the message, strips the trailing newline with `g_strchomp`, and sets it as the text of `footer_label`. |
| `on_add_clicked` | Increments the counter and appends a subject panel: a `GtkMenuButton` labeled `Materia Num #N` **without popover**, whose create-popup function is `on_subject_button_activated`, and a hidden `GtkRevealer` (slide down) with a `💾 Guardar` / `✖ Cerrar` toolbar and a 500 px high `editor_box`. |
| `on_subject_button_activated` | `GtkMenuButtonCreatePopupFunc`: GTK calls it when the subject button is pressed and has no popover, that is, before the subject exists. Releases the button with `gtk_menu_button_set_active(FALSE)` (a `GtkMenuButton` is a toggle and would otherwise stay pressed, eating the next click) and opens `new_subject_dialog(window, on_subject_dialog_done, panel)` (see [subjectDialog.c](subjectDialog.c.md)). Does nothing if the panel already has a subject. |
| `on_subject_dialog_done` | `SubjectDialogDone` callback for "Crear". Builds a NULL-terminated list with the `filter_name` of each chosen `EditKind`, creates `new_subject(panel->number)` and calls `make_subject(base_dir, name, folders)`. On failure closes the subject and returns `false`, so the dialog stays open (the reason is already in the footer through `subject_log`); on success calls `subject_panel_set_subject` and returns `true`. |
| `subject_panel_set_subject` | Gives the panel its subject (`kinds` may be `NULL` for "every kind"): renames the button after `subject->name`, removes the create-popup function and sets the popover of `new_menu_edit_kind(on_kind_chosen, panel, kinds)` (see [menu.c](menu.c.md)), so from now on the button unfolds the edit menu with only the subject's kinds. Meant to be reused when loading a subject. |
| `on_kind_chosen` | `MenuEditKindChosen` callback: receives the chosen `const EditKind *` and the panel as `user_data` (the `Menu` base already closed the popover). Refuses if the panel already has a document open, or if the kind's `available()` returns `false` (LibreOffice missing). Otherwise remembers the kind and opens a `GtkFileDialog` filtered to the kind's suffixes, starting in `<subject->dir>/<kind->filter_name>` if that folder exists. |
| `on_open_doc_finish` | Creates the editor with `kind->create()`, calls `open(path)`; on success renders it into `editor_box`, reveals the panel and shows the path in the footer; on failure closes the editor and reports the error. A cancelled dialog does nothing. |
| `on_save_doc_clicked` | Calls `edit->save()` and reports the result in the footer. |
| `on_close_doc_clicked` | Refuses when `edit->is_modified()`; otherwise `edit->close()` (removes the widget and frees the editor) and hides the revealer. |
| `app_status` | Writes a message to `footer_label`. |
| `on_load_clicked` | Creates a `GtkFileDialog` titled "Cargar Materia" and starts it with `gtk_file_dialog_open`, parented to `state->window` and with `on_load_dialog_finish` as the completion callback. The call is asynchronous: it returns immediately and the pending operation holds its own reference to the dialog, so `on_load_clicked` releases its reference right away. A forward declaration above `on_load_clicked` makes the callback visible before its definition later in the file. |
| `on_load_dialog_finish` | Calls `gtk_file_dialog_open_finish` to get the chosen `GFile`. If it returns `NULL`, the dialog was dismissed or failed: dismissal (`GTK_DIALOG_ERROR_DISMISSED`) and cancellation by the closing window (`G_IO_ERROR_CANCELLED`) are ignored, any other error is printed, and the `GError` is cleared. Otherwise it resolves the file to a local path with `g_file_get_path`, constructs a throwaway `Subject` with `new_subject(state->counter)`, and calls `mat->load_subject(mat, path, &buf, &size)`. Prints either the decoded byte count or the numeric error code, frees the decoded buffer (only returned on `0`), and destroys the temporary subject. If `new_subject` returns `NULL`, nothing is loaded or reported. It then frees the path string and releases the `GFile`. |

Since 0.1.3 each added button represents a subject created on disk (see `on_subject_dialog_done`), but the object constructed in `on_load_dialog_finish` only exists to call `load_subject`; it does not become part of the UI state (`state->counter` is not tied to the loaded subject in any way). `load_subject` returns the raw decompressed bytes (see [subject.c](subject.c.md)); this callback itself still only prints the byte count or the numeric error code and frees the buffer. On Linux, though, `load_subject` now also unpacks the decoded archive to disk as an internal side effect (writing files under a directory derived from the archive's name), so clicking "Load Subject" already extracts real files even though this callback was not changed to do anything with that side effect or report it. The Windows build of the equivalent extraction path compiles as of version 0.0.14 but has not been tested at runtime (see [subject.c](subject.c.md#extraction)). As of version 0.0.14, every result of `load_subject` (start, each error code, and success) is also reported by `src/subject.c` through `subject_log`, so it appears in the window footer (see [interface.ui](interface.ui.md#footer)). The callback's own `g_print` calls still go to the terminal only.

The footer lookup must happen before `g_object_unref(builder)`: `gtk_builder_get_object` on a released builder is undefined behavior. `load_subject` runs on the GTK main thread, so `on_subject_log` can update the label directly; if loading moves to a worker thread, the callback must defer the update with `g_idle_add()`. While `load_subject` runs the window is not redrawn, so only the final message of a load is visible.

## Ownership and limitations

Temporary label strings are freed after widget creation. The builder and application references are released. In `on_load_dialog_finish`, the temporary subject is destroyed after use, its decoded buffer is freed once printed, the path string and the `GFile` are released when a file was chosen, and the `GError` is cleared when it was not. The dialog reference is released in `on_load_clicked`, right after starting it. `AppState` is allocated with `g_new0` (all fields zeroed) and `activate` sets `window`, `destiny_content`, `footer_label`, `cancellable` and `counter`. Since 2026-10-18 it is tied to the window with `g_object_set_data_full(window, "app-state", state, app_state_free)`, so it is freed when the window is finalized (it used to leak). The asynchronous file dialogs receive `state` or a `SubjectPanel` as `user_data`; `on_window_destroy` cancels them first, and their callbacks only use `user_data` after a successful result. Each `SubjectPanel` is tied to its subject box with `g_object_set_data_full`, so GTK frees it (and closes its `Edit`) when the window is destroyed. The subject menu is tied to its popover the same way, so `main.c` never frees it; neither does it free the `SubjectDialog`, tied to its window. The `Subject` created by `on_subject_dialog_done` belongs to the panel. By then the editor's widget may already be gone; `Edit.widget` is a weak pointer (`set_widget`), so `close()` does not touch it. Builder objects are used without explicit checks for missing IDs.

The logger registered with `subject_set_logger(on_subject_log, footer_label)` is unregistered by `on_window_destroy`, so `subject.c` never keeps a pointer to a destroyed `footer_label`; later messages go to `stderr`.

Leaving through `_Exit` when LibreOffice was started skips every `atexit` handler and static destructor, not only LibreOffice's: LibreOffice does not remove its temporary profile (`/tmp/lu*.tmp`), and any data still buffered outside `stdio` would be lost. Our own state is already freed by then. This is a workaround until LibreOffice can be shut down cleanly (see [editDOC.c](editDOC.c.md)).

Editor limitations: one document per subject; closing with unsaved changes is refused with a footer message (no Save/Discard dialog yet); the first use of the office editor blocks the UI for a moment while `lok_init` starts LibreOffice on the GTK thread; a file dialog still pending when the window closes is cancelled through `state->cancellable` (see above).

## SOLID development direction

Follow the [project SOLID guidelines](README.md#development-direction-solid). Keep GTK rendering and event translation here or in a dedicated UI module. Move subject workflows into application operations as they develop, and supply their dependencies during startup. Keep compression and operating-system operations outside callbacks. Give application state an explicit cleanup lifecycle.
